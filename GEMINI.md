# Orchestrator & Swarm Rules: AI-Core Manifest 3.0 (Gemini & Swarm)

## 1. Язык общения и комментирование действий (Приоритет №1)
- **Язык общения**: Все ответы, рассуждения, отчёты и пояснения ведутся исключительно на русском языке.
- **Лаконичное комментирование каждого шага**: Кратко и по делу описывать выполняемый шаг (что делается, зачем и к какому результату это приведёт). Категорически запрещено использовать любые шаблонные вводные фразы вроде «Понятно комментирую следующее действие:», «Комментирую действие:» и т.п. — сразу формулировать суть шага живым профессиональным языком без клише.

## 2. Гетерогенный рой субагентов OpenCode & Harness-2 (ЖЕСТКОЕ ПРАВИЛО, 0$ COST)
- **ПОЛНЫЙ ЗАПРЕТ OPENROUTER (Strict Ban)**:
  - Любые модели и шлюзы OpenRouter (`openrouter/*`) полностью удалены из системы и КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ к использованию.
  - Разрешены строго чистые бесплатные модели OpenCode Zen API (`opencode/*`) и нативные субагенты Antigravity (`invoke_subagent`).

- **АРХИТЕКТУРА HARNESS-2 (Project DNA & Persistent Lessons & Execution Verification)**:
  - Любая задача субагентов и оркестратора обязана выполняться под обвязкой Harness:
    1. **Project DNA (ДНК проекта)**: Автоматическое определение технологического стека репозитория (C#, .NET 8, Win32 P/Invoke, ETW, WPF, Python) и специфических зон риска (утечки дескрипторов `SafeHandle`, sync-over-async, гонки в коллекциях).
    2. **Persistent Lessons (Память уроков)**: Автоматическая инъекция долгосрочного банка граблей и уроков роя во избежание повторения прошлых ошибок (лимит аргументов Windows 8191 символ, блокировки `CS2012`, UTF-8 BOM в PowerShell 5.1).
    3. **Zero-Crash & Zero-Stub**: Категорический запрет плейсхолдеров `// TODO`, `# TODO`, `pass`, исключений-заглушек `NotImplementedException`, пустых блоков `catch { }`. Обязательные подробные русские XML-комментарии для всего создаваемого/изменяемого кода.
    4. **Execution Harness (Контур обязательной проверки)**: Сгенерированный код считается принятым ТОЛЬКО после реальной проверки компилятором (`dotnet build`) и 100% успешного прохождения модульных тестов (`dotnet test`).

- **СТРОГОЕ ПРАВИЛО: ОБЯЗАТЕЛЬНЫЙ 3-МИНУТНЫЙ ТАЙМЕР И СТАТУС-ОТЧЕТ (`schedule`)**:
  - При запуске любых фоновых субагентов или роя оркестратор СТРОГО ОБЯЗАН немедленно вызвать инструмент `schedule(DurationSeconds=180, Prompt="Регулярный 3-минутный опрос статуса...", TimerCondition="any")`.
  - По срабатыванию таймера оркестратор считывает `logs/live_status.json` / опрашивает `manage_task` и ОБЯЗАН выдать пользователю краткий структурированный отчёт:
    `Субагент | Модель | Над чем работает | Затрачено времени / осталось | Статус / последняя строка вывода`.
  - Если работа субагентов продолжается, оркестратор немедленно перезапускает 3-минутный таймер до полного завершения консилиума.

- **ЕДИНЫЙ КАНОНИЧНЫЙ СТАНДАРТ ЗАПУСКА РОЯ (`run_swarm.py` / `swarm`)**:
  - Все субагенты роя запускаются строго через каноничный стандарт:
    - **Команда вызова**: `swarm --profile <PROFILE> --task "<TASK>"` или `python D:/Nas_sync/Projects/Swarm_agents/scripts/run_swarm.py ...`.
    - **Режим запуска**: headless CLI `opencode run --pure -m <model>` с передачей `cwd=<work_dir>`.
    - **Передача входного потока (STDIN)**: строго через пайп STDIN `proc.stdin.write(prompt)` и `proc.stdin.close()` (категорически запрещено передавать тело длинного промпта через аргументы командной строки в Windows из-за лимита 8191 символ).
    - **Изолированные песочницы субагентов (Sandbox Isolation)**: каждому параллельному субагенту создается персональная изолированная временная среда (`tempfile.mkdtemp` с копированием `auth.json` и подменой переменных среды `USERPROFILE`, `HOME`, `OPENCODE_DIR`), что исключает гонки и блокировки SQLite `database is locked`.
    - **Потокобезопасная параллельность**: `concurrent.futures.ThreadPoolExecutor(max_workers=len(AGENTS))` без взаимных блокировок между агентами.
    - **Атомарный живой JSON-мониторинг**: `logs/live_status.json` с потокобезопасной сериализацией и фиксацией полей: `status`, `task`, `last_line`, `elapsed_seconds`, `char_count`.
    - **Кодировка вывода Windows**: принудительная инициализация `sys.stdout.reconfigure(encoding="utf-8", errors="replace", line_buffering=True)`.

- **ИНТЕЛЛЕКТУАЛЬНЫЙ ТРИАЖ И ВЫБОР ИСПОЛНИТЕЛЯ (Swarm Triage & Dispatch)**:
  Оркестратор оценивает масштаб задачи перед запуском:
  1. **Уровень 1 (Точечные / тривиальные правки, фиксы конфигов, опечатки)**: оркестратор вносит изменения **сам напрямую**, исключая накладные расходы на запуск субагентов.
  2. **Уровень 2 (Локальные задачи умеренной сложности, тесты одной функции, точечный рефакторинг)**: оркестратор делегирует задачу **одному самому быстрому субагенту** под Harness-обвязкой (`opencode/beam-free` ~12с или `opencode/deepseek-v4.1-flash-free` ~13с) через MCP `delegate_task_to_subagent` без развёртывания тяжёлого консилиума.
  3. **Уровень 3 (Критические архитектурные задачи, баги многопоточности, безопасность, масштабные аудиты)**: разворачивается **полноценный консилиум роя** (консилиум 3 независимых движков `TRIAD-REVIEW` или шардинг `MASS-SHARDING`).

- **ДИНАМИЧЕСКИЕ ПРОФИЛИ РОЯ (SWARM PROFILES, 0$ BUDGET)**:
  1. **Профиль `TRIAD-REVIEW` (Консилиум 3 независимых движков с ролевой ортогональностью)**:
     - Запускаются строго **3 РАЗНЫХ ИИ-движка OpenCode**:

       - **Агент B (Многопоточность и синхронизация)**: `opencode/nemotron-3.5-lightning-free` (~14с, NVIDIA 262K, потокобезопасность, предотвращение дедлоков, гонок race conditions, утечки памяти и дескрипторов).
       - **Агент C (Тесты и верификация)**: `opencode/beam-free` (~12с, абсолютный лидер скорости, генератор тестов xUnit/NSubstitute и рефакторинг).

- **ЖЕСТКОЕ ПРАВИЛО: АВТОМАТИЧЕСКИЙ FALLBACK НА НАТИВНЫХ СУБАГЕНТОВ (Native Subagent Fallback)**:

## 4. Каноничный интерактивный запуск GUI-приложений для пользователя (Desktop Isolation & Job Object Bypass)
- **Причина проблем запуска из агента**:
  - Консольные процессы агента выполняются в изолированном виртуальном десктопе песочницы (`exebox-...` в `WinSta0`) и внутри Windows Job Object с завершением по закрытию сессии (`KILL_ON_JOB_CLOSE`). Прямой запуск через `Start-Process`, `&` или `Process.Start` создает окно в невидимом виртуальном десктопе (не отображается на физическом мониторе пользователя `WinSta0\Default`), а по завершении консольной команды процесс мгновенно завершается системой.
- **Стандарт интерактивного запуска через планировщик Windows (`schtasks`)**:
  - Для гарантированного вывода графических окон на физический монитор пользователя оркестратор ОБЯЗАН запускать GUI-бинарники строго через системный планировщик задач:
    ```powershell
    $exe = (Resolve-Path "<path_to_gui_app>").Path
    $tn = "InteractiveLaunch_" + [Guid]::NewGuid().ToString("N").Substring(0, 8)
    schtasks /create /tn $tn /tr "`"$exe`"" /sc once /st "00:00" /f | Out-Null
    schtasks /run /tn $tn | Out-Null
    Start-Sleep -Milliseconds 1500
    schtasks /delete /tn $tn /f | Out-Null
    ```
- **Активация и вывод на передний план**:
  - После запуска окно активируется и переводится в фокус вызовами Win32 API (`ShowWindow(hWnd, SW_RESTORE)`, `BringWindowToTop(hWnd)`, `SetForegroundWindow(hWnd)`).

- Если проект содержит локально установленную инсталлятором рабочую копию (например, в `Program Files` или `AppData`), перед публикацией релиза оркестратор ОБЯЗАН обновить исполняемые файлы в каталоге установки, перезапустить связанные системные службы/процессы и убедиться в чистоте логов при их старте.
