# Engineering & Development Standards: Startup Monitor

## 1. Архитектурные принципы кодовой базы
- **Модульная структура решения**:
  - `StartupMonitor.Service` — системная служба Windows (Zero-overhead, сбор телеметрии процессов без всплесков CPU, сопоставление правил брандмауэра через кэш и Port Defender, IPC-сервер именованных каналов).
  - `StartupMonitor.UI` — графический интерфейс (WPF Fluent Design Windows 11, MVVM, отсутствие блокирующих вызовов в UI-потоке, динамическая поддержка Dark/Light тем).
  - `StartupMonitor.Shared` — общие контракты данных (DTO), протоколы IPC-сообщений, модели конфигурации и кросс-модульные утилиты.
  - `StartupMonitor.Tests` — полный набор автоматических юнит- и интеграционных тестов с нулевым допуском падений.

## 2. Стандарты качества и надежности кода (Zero-Crash & Zero-Stub)
- **Zero-Crash и валидация на границах**:
  - Обязательная проверка входных аргументов (`ArgumentNullException`, проверка границ диапазонов, null-forgiving операторы `!` только с документированным обоснованием).
  - Проверка типов с учётом нюансов среды выполнения (например `isinstance(True, int)`).
- **Защита контрактов и инвариантов**:
  - Обязательная проверка на `null` и пустоту коллекций перед обращением по индексу.
  - Поддержка отмены через `CancellationToken` в асинхронных методах и детерминированное освобождение ресурсов (`IDisposable`, `using`).
- **Категорический запрет плейсхолдеров и заглушек (Zero-Stub)**:
  - Строжайше запрещено оставлять в коде `// TODO`, `/* implement later */`, `throw new NotImplementedException()`, пустые блоки-заглушки или фиктивные mock-данные в рабочем коде. Любая создаваемая функциональность реализуется сразу полностью и в готовом к бою виде.
- **Прозрачность ошибок и запрет тихих подавлений**:
  - Понятные, содержательные сообщения об исключениях с контекстом сбоя.
  - Строгий запрет на «тихое» подавление исключений: пустые блоки `catch { }` или `except: pass` без логирования категорически недопустимы.
- **Чистота и производительность**:
  - Минималистичный, эффективный C# код без избыточного бойлерплейта и неиспользуемых `using`.

## 3. Методология внесения изменений (Plan-Before-Code & Minimal Diff)
- **Двухфазное выполнение (Plan-Before-Code)**:
  - Перед редактированием кода формулируется микро-план из 2–3 конкретных пунктов (локализация проблемы, точечное исправление, способ проверки). Хаотичное редактирование вслепую запрещено.
- **Принцип хирургического диффа (Minimal Diff)**:
  - Изменения вносятся строго в целевой метод или блок кода. Категорически запрещено переписывать весь файл целиком или затрагивать не связанные методы, чтобы исключить потерю окружающего контекста и скрытые регрессии.
- **Обязательная локальная верификация**:
  - Каждое изменение немедленно верифицируется компилятором и прогоном профильных тестов до фиксации.

## 4. Стандарты комментирования кода на русском языке
- **Русские комментарии в коде**:
  - Каждый создаваемый или модифицируемый блок кода обязан содержать подробные XML-комментарии (`<summary>`, `<param>`, `<returns>`) на русском языке.
  - Обязательно комментируются: назначение классов и функций, алгоритмы, неочевидные архитектурные решения, формулы, граничные условия и обработка исключений.
  - Имена классов, методов, полей, свойств, переменных и файлов сохраняются строго на каноничном английском языке.
- **Тексты дисплеев и встроенных контроллеров**:
  - Если код предназначен для экранов или микроконтроллеров без поддержки шрифтов UTF-8 (например, текстовые LCD 12864, ST7920, HD44780), сообщения (`SET_DISPLAY_TEXT`, `M117`, LCD print) пишутся строго на латинице (ASCII) во избежание искажения символов.

## 5. Обязательная валидация перед публикацией (Pre-Publish Verification)
- **Прямой запуск бинарников и проверка логов**:
  - Перед любой публикацией релиза или коммита оркестратор ОБЯЗАН собрать проект, напрямую запустить исполняемые файлы (`SMon2/StartupMonitor.UI.exe`, `StartupMonitor.Service.exe`) и лично проинспектировать созданные лог-файлы (`ui-debug.log`, `service-*.log`) на предмет ошибок и исключений.
  - Публикация релиза разрешается только после подтверждения чистоты логов при реальном запуске.
- **Обязательное тестирование**:
  - Все юнит-тесты решения (`dotnet test`) должны завершаться с результатом 100% пройденных тестов без пропусков критических путей.

## 6. Формат Git-коммитов и версионирование (Строгие правила)
- **Обязательное повышение версии перед публикацией (Strict Version Bump)**:
  - Перед любой публикацией релиза, сборкой инсталлятора или созданием релизного коммита оркестратор ОБЯЗАН проверить последнюю опубликованную версию (в GitHub Releases / git tags) и **СТРОГО ОБЯЗАТЕЛЬНО повысить номер версии** (Patch: `2.0.2` -> `2.0.3` при исправлениях, Minor при новом функционале) в `Directory.Build.props` (`<Version>`, `<AssemblyVersion>`, `<FileVersion>`).
  - **Категорический запрет**: Сборка инсталлятора или публикация релиза с версией, которая уже была опубликована на GitHub или присутствует в тегах репозитория, КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНА. Каждый релиз обязан иметь уникальный строго возрастающий номер версии.
  - **Синхронизация номера версии**: новая версия обязана одновременно и согласованно отражаться в `Directory.Build.props`, имени инсталлятора `StartupMonitorSetup-<Version>.exe`, сообщении Git-коммита `v<Version>: ...` и релизном Git-теге.
- **Версия ВСЕГДА первой в сообщении коммита**:
  - В каждом сообщении Git-коммита в самом начале строго обязательно указывается актуальная повышенная версия продукта, затем двоеточие и описание изменений по стандарту Conventional Commits.
  - **Шаблон**: `v<Version>: <type>(<scope>): <subject>` (например: `v2.0.3: fix(update): eliminate false update prompt on identical versions`).
  - **Строгий запрет**: Создавать любые коммиты без указания версии в самом начале описания СТРОГО ЗАПРЕЩЕНО.
