# Автоматическое отключение автозапуска и восстановление

Дата: 6 ноября 2026 года. База: `efac027`; исправления включены в сборку 2.1.1.

## Что изменено

Автоматические пути чёрного списка, StrictMode и AutoGuard используют обратимое отключение. Они сохраняют запись в основном списке с `DisablePayload`, не создавая новую запись в разделе удалённых. Старое сериализованное имя действия `NotifyAndRemove` сохранено для совместимости; его автоматическая операция теперь отключает точку автозапуска. Ручная команда удаления сохраняет прежнее назначение и резервную копию.

Файл автозапуска переименовывается в `.disabled`. Первый файл не перезаписывается ни при повторном отключении, ни при конфликте включения. Задача планировщика сохраняет XML и отключается флагом `Enabled`. Служба сохраняет тип запуска и получает `start=disabled`; включение возвращает сохранённый тип, не запуская службу принудительно. Значение Run/RunOnce переносится из активного ключа в его неактивный подключ `StartupMonitorDisabled`; сохраняются DWORD, QWORD, Binary, MultiString и ExpandString без раскрытия переменных. Старые строковые payload остаются читаемыми.

Если ранее удалённая запись появилась снова, она автоматически отключается и остаётся видимой в основном списке. Исходная ручная резервная копия не затирается. Очистка устаревших записей сохраняет такие отключённые записи с `DisablePayload`.

## Почему Antigravity не восстанавливалась

В установленном хранилище найдена задача `AntigravityAutoPatch`, исходная identity `909e318745db`, резервная копия `30171614`. История содержит событие `BlockedByPolicy` от 4 ноября 2026 года 19:46:53 UTC; причина резервной копии — `AutoGuardBlocked:script`. Полный XML задачи и путь сохранены. Файловые backup для восстановления этой задачи не требуются.

Обнаружены два дефекта:

1. `RestoreTask` вызывал `TaskFolder.RegisterTask(path, xml)` с неявным `logonType=S4U`. Значение по умолчанию подтверждено чтением метаданных фактической библиотеки TaskScheduler 2.12.2. Задача Antigravity использовала `InteractiveToken`. Теперь при регистрации явно сохраняются исходные principal и logon type. Задачи, которым требуется пароль, получают понятный отказ: пароль в backup не хранится и не подменяется другим типом входа.
2. `RestoreEntry` восстанавливал объект ОС, не зарегистрировав известную identity в основном списке. Watcher мог расценить его как новую скриптовую задачу и снова применить AutoGuard. Теперь перед операцией ОС сохраняется identity и действует ограниченное временем самого запроса runtime-намерение ручного восстановления. Резервная копия удаляется только после подтверждения ОС. При отказе предварительная запись откатывается; runtime-намерение освобождается также при ошибке отката.

Если действующее правило чёрного списка требует отключения, Restore/Enable возвращает явную причину отказа и сохраняет backup; сначала пользователь снимает правило. Имена с `antigravity` не считаются собственными компонентами Startup Monitor и не исключаются из восстановления по имени.

## Безопасные повторные запросы

Повтор Restore после потерянного ответа или сбоя сохранения допускается без перезаписи чужого объекта. Существующая задача принимается только при точном совпадении её XML с сохранённым, включая principal, действия, триггеры и настройки. Существующий файл принимается только при совпадении SHA-256. Существующее значение реестра — только при совпадении типа и данных. Иной объект по тому же пути вызывает диагностируемый конфликт.

Если та же известная точка уже была автоматически отключена после повторного появления, Restore использует её `EnableFromSystem`. Для задач дополнительно сравниваются определения, допуская только изменение `Settings/Enabled`.

## Проверка и ограничения доказательства

Регрессии проверяют AutoGuard и StrictMode на собственных безвредных файлах, повтор отключения, конфликт файлов, ручное восстановление Antigravity с вызовом watcher до ответа ОС, отказ восстановления, отказ сохранения после успеха ОС с безопасным повтором, действующий чёрный список и точное восстановление пяти типов Registry в собственном ключе HKCU вне автозапуска.

Тестовые fixtures, ранее ожидавшие успех удаления несуществующего случайного значения HKLM/HKCR, исправлены на содержательный отказ. Тесты не создают реальные Winlogon/BootExecute записи. Существующий файл конфликтует с Restore; fixtures обычного восстановления моделируют действительно отсутствующий целевой путь.

Реальная задача Antigravity в ходе аудита не восстанавливалась и не включалась. Её сохранённые данные не изменялись. Дополнительно выполнен реальный прогон собственного временного задания планировщика без триггеров: **13 проверок пройдены**. Проверены отключение и повторное отключение с сохранением первого payload, включение, удаление, восстановление исходных SID и `InteractiveToken`, безопасный повтор восстановления, отказ перезаписывать изменённый XML и окончательная очистка собственной задачи. Задание ни разу не запускалось. Доказательства: `out/release-verification-20261106-2.1.1/startup-native/startup-native-results.json` и `stdout.log`; это отдельная интеграционная проверка, а не часть счётчика unit-тестов.
