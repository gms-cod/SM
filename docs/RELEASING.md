# Порядок публикации Startup Monitor

## Источник публикуемых файлов

Установщик собирается локально из проверенных бинарников и включается в релизный коммит вместе с SHA-256. GitHub Actions повторно выполняет тесты, проверяет версию и контрольную сумму, затем публикует **тот же установщик**. CI не пересобирает второй EXE с другим содержимым под той же версией.

Push обычной ветки и pull request выполняют только проверки. Публикация запускается тегом `v<Version>` либо явным `workflow_dispatch` с `publish_release=true`. Значение по умолчанию — `false`. Повторная публикация существующего релиза отклоняется.

## Обновление рабочей копии перед пользовательской проверкой

Пользователь запускает приложение из `C:\Program Files\StartupMonitor\`. После изменений исходников и подготовки новой сборки этот каталог обязательно обновляется перед передачей результата на проверку пользователю, даже если релиз сейчас не публикуется.

1. Выполнить сборку и полный прогон тестов с `ExcludePublishToSMon=true`.
2. Явно запустить `scripts/publish.ps1 -Configuration Release -LaunchUI` с административными правами. При согласованном выпуске без Authenticode-подписи явно передать `-SkipSign`. После успешной публикации обоих модулей скрипт останавливает приложение, синхронизирует EXE и иконки в `SMon2` и `C:\Program Files\StartupMonitor\`, сохраняет пользовательскую конфигурацию, разблокирует файлы и запускает установленную службу. Транзакция сохраняет прежние файлы в `out/deployment-backup-*`; при отказе копирования или запуска восстанавливает файлы и прежнее состояние SCM. Неполный откат не запускает смешанную сборку, а сообщает путь резервной копии.
3. Сверить FileVersion и SHA-256 установленных `StartupMonitor.Service.exe` и `StartupMonitor.UI.exe` со свежими бинарниками в `out/publish-Release`; проверить, что зарегистрированная служба использует EXE из `C:\Program Files\StartupMonitor\`.
4. Проверить запущенный UI из установленного каталога. `-LaunchUI` использует `schtasks` и `launch-ui-interactive.ps1`: HWND проверяется и окно активируется на пользовательском Desktop; JSON результата сохраняется рядом с XML задачи в каталоге резервной копии. Проверить свежие участки `C:\Program Files\StartupMonitor\logs\service-*.log` и `ui-debug.log`, затем передать пользователю обновлённую рабочую копию для проверки.

Развёртывание запускается отдельным явным действием: обычные `dotnet build` и `dotnet test` не останавливают и не заменяют установленное приложение.

## Последовательность

1. Проверить GitHub Releases и локальные/удалённые теги обоих настроенных репозиториев. Выбрать версию, строго превышающую все использованные версии. Согласовать `Version`, `AssemblyVersion`, `FileVersion`, `InformationalVersion` в `Directory.Build.props` и значение по умолчанию в `installers/StartupMonitor.iss`.
2. Выполнить полный Release-прогон:

   ```powershell
   dotnet test StartupMonitor.sln -c Release -m:1 -p:ExcludePublishToSMon=true --nologo
   ```

3. Опубликовать свежие бинарники через `scripts/publish.ps1`. Сначала собираются оба модуля в `out/publish-Release`; только после успеха останавливается приложение и заменяются четыре файла в `SMon2` и установленной копии. Конфигурация пользователя не копируется и не удаляется. Скрипт проверяет коды native-команд и корректно сохраняет кавычки пути службы через CIM.
4. Прямо запустить `SMon2/StartupMonitor.Service.exe --console` и `SMon2/StartupMonitor.UI.exe --minimized`, предварительно остановив зарегистрированную службу, чтобы не получить конфликт экземпляров. Проверить свежие участки `service-*.log` и `ui-debug.log`, включая завершение приложения. После проверки запустить установленную службу и проверить её свежий журнал.
5. Собрать установщик до создания нового тега:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-installer.ps1 -SkipPublish
   ```

   Скрипт запрещает повторное использование версии из существующего тега и проверяет FileVersion обоих EXE. По умолчанию подпись должна завершиться статусом `Valid`; ошибка или отсутствие сертификата не считаются успехом.

   Если сертификат отсутствует и выпускается пакет без Authenticode-подписи, это указывается явно: `-SkipSign` при публикации бинарников и при сборке установщика. SHA-256 подтверждает целостность, но не заменяет подпись издателя. Отметка об отсутствии подписи включается в описание такого релиза.
6. Проверить готовые `installers/StartupMonitorSetup-<Version>.exe` и `.exe.sha256`. Создать `docs/releases/v<Version>.md` с изменениями, результатами тестов и окончательной контрольной суммой. В релиз включаются только эти два файла нужной версии; старые установщики по маске не загружаются.
7. Создать коммит по шаблону `v<Version>: <type>(<scope>): <subject>`, затем тег `v<Version>` на этом коммите. Отправить коммит и тег атомарно в настроенный репозиторий. Для зеркала повторить отправку того же коммита и того же тега.
8. Дождаться успешного workflow для тега. Проверить exact tag, commit, два имени assets, размеры и SHA-256 опубликованного EXE. Убедиться, что `releases/latest` указывает на новую версию. Старые теги и опубликованные файлы не перезаписывать.

## Что проверяет GitHub Actions

- Полный тестовый проект в Release.
- Соответствие тега версии в props.
- Наличие точного установщика, sidecar SHA-256 и описания выпуска.
- Совпадение имени файла и SHA-256 с sidecar.
- FileVersion самого установщика.
- Отсутствие уже опубликованного релиза с тем же тегом.

Установщик требует административной установки службы и поддерживает x64-совместимую Windows. Режим `/CURRENTUSER` для установки без SCM-прав не поддерживается.
