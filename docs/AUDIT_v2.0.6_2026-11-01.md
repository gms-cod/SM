### 1.2. Уточнения к исходному описанию проекта

- Версия в `Directory.Build.props` действительно **2.0.6**.
- Проект фактически использует **.NET 8**: Service — `net8.0`, UI и Tests — `net8.0-windows10.0.17763`. В окружении установлен SDK `8.0.423`. Указание .NET 9 в задании не соответствует текущим `.csproj`.
- Класса `FirewallPromptWindow` в исследованной версии нет. Соответствующее окно — `NetworkConnectionAlertWindow`.
- Port Defender использует периодические снимки таблиц сокетов. Это не WFP-фильтрация до первого пакета и не полноценный счётчик поступающих сетевых пакетов.

### 1.3. Проверенные сильные стороны

- AI-анализ уведомления запускается асинхронно после `Loaded`; окно не ожидает ответа AI перед первым показом. Реализованы отмена и проверки закрытия окна.
- Для обычных конечных неотрицательных значений график защищён от деления на ноль; нулевой поток получает диапазон `[0, 1024]`.
- Контрольные точки кривой ограничиваются вертикальным диапазоном, включён `ClipToBounds`. Подтверждения overshoot за границы для штатных данных не получено.
- `ProcessNetworkTracker` защищает общие нативные буферы через `_sync`, повторно использует память и освобождает её в `Dispose`. Есть обработка TCP/UDP IPv4/IPv6 и кэш имён процессов.
- Многие COM-объекты Windows Firewall освобождаются в `finally`; изменения правил сериализованы. В `NetworkConnectionAlertService` есть кэш путей разрешённых приложений.
- `.Result` в `ProcessConnectionsWindow.xaml.cs:145–146` расположен после `await Task.WhenAll`, поэтому эти строки сами по себе не блокируют UI.

### 3.2. CRITICAL

#### A01. Синтаксически корректная конфигурация может остановить запуск

**Файлы и методы:** `src/StartupMonitor.Shared/Models/JsonDataStore.cs:98`, `EnsureLoadedLocked`; `:137`, `CloneSnapshot`; `:209`, `ReadSection<T>`; `src/StartupMonitor.Shared/Models/AppConfig.cs:214`, `AppSettings.Clone`; `src/StartupMonitor.Service/Program.cs:72`, начальная загрузка.

**Механизм:** `ReadSection` восстанавливает секцию при ошибке десериализации, но явный `null` допустим для JSON. Файл `settings.json` с содержимым `{"settings":null}` успешно читается, значение попадает в `_cache.Settings`, затем `CloneSnapshot` вызывает `.Clone()` у `null`. `Program` ловит исключение верхним обработчиком и завершает службу. Наличие `.backup` не помогает: семантическая проверка до публикации кэша отсутствует.

Другие проблемные границы: `port_defender:null`, `startup-entries.json` со значением `[null]`, вложенные null-коллекции. Невалидный `HistoryDays` способен вызвать `ArgumentOutOfRangeException` в `DateTime.AddDays` при обработке непустой истории.

**Minimal Diff:** валидировать результат каждой десериализации внутри существующей ветки recovery, включая чтение резервной копии. Невалидный объект нельзя устанавливать в `_cache`. Например, следующая проверка в `ReadSection<T>` после десериализации переводит повреждённые настройки в существующий путь восстановления:

```csharp
// Семантически повреждённая секция должна пройти тот же путь восстановления, что и повреждённый JSON.
if (value is SettingsSection section &&
    (section.Settings is null || section.Settings.PortDefender is null))
{
    throw new JsonException($"Секция настроек '{path}' содержит обязательный объект null.");
}
```

Здесь `value` — локальный результат текущего `JsonSerializer.Deserialize<T>` перед возвратом. Этот guard покрывает указанные обязательные объекты; отдельно необходимы проверки элементов списков, вложенных коллекций, enum и допустимых диапазонов. Нельзя считать один guard полной валидацией модели. Ошибку восстановления нужно логировать с именем секции, не раскрывая секреты.

**Проверка:** настройки с null верхнего/вложенного уровня; `[null]`; выход интервалов за диапазон; валидный backup при семантически невалидной основной секции; повреждение обеих копий. Требуется проверка поведения запуска службы, а не только исключения из десериализатора.

### 3.3. HIGH

#### A02. Авторизация IPC не соответствует привилегиям службы

**Файлы и методы:** `src/StartupMonitor.Service/Pipe/PipeSecurityFactory.cs:47`, `CreateDefault`; `PipeServer.cs:469`, `HandleClientAsync`; `:1415`, `GetAiConfig`; `:1935`, `KillProcessById`; `:4237`, `ShutdownService`.

**Механизм:** `InteractiveSid` получает Read/Write. После чтения сообщения `HandleClientAsync` вызывает `ProcessMessage` без проверки личности и прав клиента. Ограничение права создавать новые экземпляры pipe не ограничивает доступные команды. Процесс обычного интерактивного пользователя может запросить административные операции, остановку службы и незамаскированный AI API key.

**Minimal Diff:** для административной модели доступа исключить выдачу Read/Write группе `InteractiveSid`; оставить SYSTEM/Administrators. Это меняет доступность UI для обычного пользователя и должно быть явно закреплено как продуктовая политика. Для сохранения обычного read-only UI нужен захват личности клиента и список разрешённых команд до диспетчеризации. Фрагмент проверки административного клиента:

```csharp
/// <summary>Проверяет административные права подключённого клиента именованного канала.</summary>
/// <param name="pipe">Подключённый канал с доступным олицетворением клиента.</param>
/// <returns>Признак наличия административных прав у клиента.</returns>
private static bool IsAdministratorClient(NamedPipeServerStream pipe)
{
    ArgumentNullException.ThrowIfNull(pipe);
    var allowed = false;
    pipe.RunAsClient(() =>
    {
        using var identity = WindowsIdentity.GetCurrent();
        allowed = new WindowsPrincipal(identity).IsInRole(WindowsBuiltInRole.Administrator);
    });
    return allowed;
}
```

Отказ олицетворения должен означать отказ доступа; уровень impersonation у клиента необходимо согласовать. Проверку нельзя оставлять неиспользуемой: она должна предшествовать выполнению защищённой команды. Запросы секретов также требуют авторизации. Произвольное выполнение кода через эту границу в рамках аудита не демонстрировалось.

**Проверка:** обычный пользователь, elevated/non-elevated administrator, SYSTEM; чтение разрешённых DTO; отказ на управление firewall, процессы, остановку службы и чтение секретов.

#### A03. Save устаревшего снимка откатывает параллельные изменения

**Файлы и методы:** `src/StartupMonitor.Shared/Models/JsonDataStore.cs:123`, `Load`; `:402`, `Save`; `:639`, `UpdateEntry`; `src/StartupMonitor.Service/Pipe/PipeServer.cs:5025`, `BackgroundHashScanLoop`.

**Механизм:** `Load` возвращает глубокую копию. `Save` полностью заменяет кэш переданной копией. Раздельные lock внутри методов не делают всю последовательность read-modify-write атомарной.

```csharp
// Диагностический сценарий: сохранение старого снимка удаляет новую запись.
var snapshot = store.Load();
store.AddEntry(new StartupEntry { Id = "new", Name = "New" });
snapshot.Theme = "light";
store.Save(snapshot);
```

Воспроизведён результат `Entries.Count == 0`. Реальный длинный сценарий — загрузка конфигурации, сетевое сканирование репутации и сохранение старого конфига. За время сетевых запросов меняются записи, blacklist и настройки.

**Minimal Diff:** в `BackgroundHashScanLoop` убрать финальный `_store.Save(cfg)`: `ScanEntryAsync` уже обновляет записи через хранилище. Для остальных read-modify-write путей ввести секционные атомарные изменения либо ревизию с обнаружением конфликта. Пример отдельной операции настроек в `JsonDataStore`:

```csharp
/// <summary>Атомарно изменяет только настройки, сохраняя актуальные записи и историю.</summary>
/// <param name="update">Синхронное изменение изолированной копии настроек.</param>
public void UpdateSettings(Action<AppSettings> update)
{
    ArgumentNullException.ThrowIfNull(update);
    lock (_lock)
    {
        EnsureLoadedLocked();
        var current = _cache ?? throw new InvalidOperationException("Хранилище не загружено.");
        var settings = current.Settings.Clone();
        update(settings);
        current.Settings = settings;
        SaveSettings();
    }
}
```

### 4.3. Нестабильность и изоляция

- AI-тесты `NetworkConnectionAlertServiceTests` используют wall-clock polling с пределом около 2 секунд. Под нагрузкой машины это может дать ложное падение. Один сценарий наблюдает ранее полученный изменяемый DTO, полагаясь на aliasing вместо нового запроса состояния.
- STA-тест графика использует `Thread.Join()` без timeout. Проблемный Dispatcher/поток способен остановить весь test runner. Создания контрола на STA недостаточно для проверки layout/render.
- Часть notification-тестов опирается на Sleep/Wait и общий изменяемый список callbacks. Нужны явные точки синхронизации, потокобезопасный сбор результатов и проверка результата ожидания.
- A22 нарушает изоляцию файлов. Исправить директории до расширения параллельного запуска.
- Использование настоящего WindowsFirewallService в unit-тестах связывает поведение с правами и политикой машины. Сетевые изменения проверять через внедряемый адаптер; настоящие COM-интеграционные тесты выделить в управляемый контур с гарантированной очисткой.

Предпочтительный механизм ожидания — `TaskCompletionSource` с `RunContinuationsAsynchronously`, ограниченный timeout и управляемое время для debounce/retention, без зависимости от скорости конкретной машины.

## 5. Производительность, нативные ресурсы и архитектурные ограничения

### 5.1. Сетевой сбор и сопоставление процессов

`ProcessNetworkTracker` уже переиспользует нативные буферы и кэширует имена PID. Это полезная база; переписывание всего сборщика не требуется. Однако несколько потребителей независимо запрашивают снимки: Port Defender, NetworkConnectionAlertService, матрица доступа и ProcessMetricsTracker.

В `CaptureNetworkBandwidth` для установленных TCP-соединений выполняются `SetPerTcpConnectionEStats`/`GetPerTcpConnectionEStats`; `_sync` удерживается во время обхода. Стоимость линейна по числу соединений, а параллельные потребители конкурируют за lock. Общего snapshot cache с согласованным timestamp нет.

Рекомендуется один ограниченный по частоте сборщик с опубликованным неизменяемым снимком и отдельными потребителями. Необходимо измерить 100/1000/10000 сокетов, число P/Invoke, lock wait, allocations и интервал обновления. Конкретные проценты CPU без такого профиля не установлены.

TCP ESTATS предоставляет TCP-данные. Наличие UDP-таблицы в том же классе не означает измерения UDP throughput. Polling видит наблюдённые состояния соединений, пропускает короткоживущие соединения между снимками и не измеряет SYN/packet rate. Обещания детектировать любой флуд или предотвращать первый пакет требуют другого источника/механизма, например подходящей событийной телеметрии и политики фильтрации; один анализ таблиц этого не гарантирует.

### 5.2. Windows Firewall и LocalSystem

Вызовы COM синхронны, общего deadline/cancellation для работы COM нет. Перенос в Task.Run не делает зависший COM-вызов отменяемым. Если требуется жёсткая гарантия времени ответа, нужен выделенный исполнитель и при необходимости изоляция процесса с контролируемым восстановлением.

Права LocalSystem не гарантируют успешность каждого изменения: возможны политика организации, состояние BFE/firewall и ошибки отдельных параметров. Поэтому A08 и отказ от тихих catch важнее предположения «службе всегда разрешено». Зависание COM в рамках аудита не воспроизведено.

### 5.3. Контракты Shared

Текущие модели в основном изменяемы. Глубокое копирование полезно для изоляции читателей, но не обеспечивает ни семантическую валидность десериализованных данных, ни атомарность последующего сохранения. Это разные свойства, требующие отдельных механизмов.

Практический путь: валидировать DTO на границах; разделить read snapshots и команды изменения; применять patch конкретных полей под синхронизацией; не выдавать наружу объекты внутреннего кэша. Массовая замена всех DTO на immutable records сама по себе не исправит A01/A03.

### 5.4. Комментарии и диагностический код

Русские XML-комментарии присутствуют во многих файлах, однако часть представляет собой шаблонные описания вида «выполняет операцию» и не объясняет владение ресурсами, инварианты или сценарии отказа. При точечных исправлениях документировать именно эти свойства. Полная перепись комментариев вне изменяемых блоков не является первоочередной работой.

## 7. Рекомендуемый объём изменений

Работу следует разделить на небольшие проверяемые изменения: build/deploy, IPC security, store validation, store concurrency, IPC transport, lifecycle, Port Defender transactions, rule evaluation, telemetry source, WPF layout, tests/performance.

Для каждого изменения: микро-план из 2–3 пунктов, точечный diff, русские XML-комментарии к изменяемым контрактам и нетривиальным решениям, профильные тесты и компиляция. Объединение всего аудита в переписывание крупных файлов затруднит проверку и создаст дополнительные регрессии.

**Главный приоритет — восстановить проверяемые инварианты:** команда разрешена вызывающему пользователю; сохранение не теряет чужие изменения; ответ относится к своему запросу; бан подтверждён firewall; включённая защита работает без UI; график отображает измерения; действия окна остаются доступными.
