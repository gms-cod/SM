### 1. Анализ 0.0% CPU Idle и фонового энергосбережения

#### 1.1. Архитектурная коллизия между «Глубоким сном» (п. 1.1.1) и «Headless Defense» (п. 1.1.4)
В плане содержится **фундаментальное логическое противоречие**, которое необходимо разрешить на берегу:
* В **п. 1.1.1** указано: *«Условие `hasWork` переводится на `() => AlertsEnabled && _monitorWindowActive`. В режиме простого фона фоновый скан полностью засыпает (`Timeout.InfiniteTimeSpan`)»*.
* В **п. 1.1.4** указано: *«Непрерывная защита без запущенного UI (Headless Defense): Служба автономно отслеживает подключения... Если обнаружено новое неизвестное внешнее подключение и UI закрыт: служба выполняет запуск интерфейса...»*.

**Вердикт архитектора:** Если цикл сканирования сокетов в `NetworkConnectionAlertService` полностью усыпить через `Timeout.InfiniteTimeSpan` при `_monitorWindowActive == false`, то **Headless Defense ослепнет**. Служба перестанет видеть новые соединения, когда UI закрыт!

**Как сделать правильно (0.0% CPU без потери Headless-защиты):**
1. **Разделение контуров (Dual-Mode Polling / Event-Driven):**
   * **Режим UI Active (`_monitorWindowActive == true`):** Быстрый поллинг (раз в 2–3 секунды) с полным обогащением данных (GeoIP, резолвинг имен, подсчет метрик ESTABLISHED/LISTENING для красивых карточек UI).
   * **Режим Headless Idle (`_monitorWindowActive == false`):** Переход либо на **ETW (Event Tracing for Windows)** провайдер `Microsoft-Windows-TCPIP` / `Microsoft-Windows-Kernel-Network` (который дает **абсолютный 0.0% CPU** в простое и будит поток только при реальном `TcpConnect` / `Accept`), либо, если остаемся на `GetExtendedTcpTable` (IPHelper API), — перевод цикла в **Eco-Sensing режим** (интервал 5–10 секунд, `ThreadPriority.Lowest`, выполнение аллокационно-нулевого `ArrayPool<byte>` P/Invoke вызова `GetExtendedTcpTable`, который занимает `< 0.08 мс` и в Task Manager отображается как чистые **0.0% CPU**). При этом в Headless-режиме мы проверяем *только* дельту новых внешних `ESTABLISHED` PID'ов против HashSet-кэша в памяти.
2. **Механизм Heartbeat для `_monitorWindowActive`:**
   * Что если процесс `StartupMonitor.UI.exe` будет убит через Диспетчер задач (`TerminateProcess`)? Он не успеет отправить по Named Pipe команду «Я закрылся».
   * **Требование:** Флаг `_monitorWindowActive` в службе должен быть не просто `bool`, а базироваться на `Environment.TickCount64` последнего IPC-пинга от UI (Lease/TTL = 10 секунд) или подписке на `Process.EnableRaisingEvents` / `WaitForSingleObject` дескриптора клиентского процесса Pipe.

#### 1.2. Ликвидация дублирующего поллинга UI (п. 1.1.2)
Полностью поддерживаю. Вызов синхронного `ScanNewConnections()` внутри обработчика IPC-запроса `GetPendingNetworkAlerts` создавал эффект «шторма вызовов» ядра при открытом окне. Перевод IPC-метода на чтение `ConcurrentQueue` / `Channel<T>` (Consumer-Producer паттерн) — единственно верное решение в .NET 8.

#### 1.3. Кэширование COM-объектов `HNetCfg.FwPolicy2` (TTL 60 сек) (п. 1.1.3)
Маршалинг `INetFwPolicy2.Rules` из неуправляемого COM (`FirewallAPI.dll`) через RCW (Runtime Callable Wrapper) в .NET действительно чудовищно дорог из-за тысяч аллокаций `BSTR` и вызовов `IDispatch::Invoke`. Кэш `_firewallRulePathsCache` с TTL 60 секунд снимет 99% нагрузки.

**Подводные камни сторонних изменений и как их обойти:**
1. **Устаревание кэша (Stale Cache Hazard):** Если пользователь или сторонняя программа (например, инсталлятор игры, Docker или сам пользователь через `wf.msc`) изменит правила брандмауэра извне, наш кэш будет врать до 60 секунд.
   * **Решение для Blacklist/Defense:** При проверке того, заблокировано ли приложение из нашего Черного списка, служба должна опираться в первую очередь на **свой внутренний персистентный реестр Черного списка**, а не только на COM-кэш Windows Firewall. Если процесс в нашем Blacklist — мы считаем его враждебным мгновенно (0 мс), а синхронизацию с `INetFwPolicy2` делаем идемпотентно.
2. **Утечка памяти RCW (COM Memory Leak в .NET):**
   * При обновлении кэша раз в 60 секунд критически важно освобождать COM-интерфейсы! В .NET 8 сборщик мусора не видит тяжести нативных COM-объектов за маленькой управляемой оберткой.
   * **Директива для кода:** Внутри метода обновления кэша обязательно использовать `Marshal.FinalReleaseComObject(rule)` для каждого элемента итератора `INetFwRules` и для самой коллекции, иначе служба получит ползучую утечку `Private Bytes` в нативной куче.
3. **Потокобезопасность (Cache Stampede):**
   * Не используйте обычный `ConcurrentDictionary` с ленивой фабрикой, которая может запустить 5 параллельных COM-опросов при одновременном истечении TTL. Используйте `SemaphoreSlim(1, 1)` для эксклюзивного обновления снимка `FrozenDictionary<string, FirewallRuleInfo>` (.NET 8 `System.Collections.Frozen` даст максимальную скорость чтения O(1) и нулевые блокировки при чтении!).

### 2. Headless-защита и безопасность без запущенного UI

#### 2.1. Прорыв Session 0 Isolation (`UserSessionLauncher`)
Запуск `StartupMonitor.UI.exe --minimized --alert` из системной службы (`NT AUTHORITY\SYSTEM`, Session 0) на рабочий стол пользователя (Session 1+) — это минное поле безопасности Windows.

**Критические требования к реализации `UserSessionLauncher.cs`:**
1. **Запрет на Escalation of Privilege (EoP / Shatter Attack):**
   * **Категорически запрещено** запускать `StartupMonitor.UI.exe` в пользовательской сессии с токеном `SYSTEM`! Если UI запустится под `SYSTEM` на интерактивном десктопе пользователя, любой локальный вредонос или даже сам пользователь через стандартный `OpenFileDialog` (который запланирован во вкладках 2 и 3!) сможет открыть `cmd.exe` с правами `NT AUTHORITY\SYSTEM`.
   * **Правильный алгоритм Win32 API:**
     1. Найти активную консоль через `WTSGetActiveConsoleSessionId()` (или перебрать `WTSEnumerateSessions` со статусом `WTSActive`).
     2. Получить первичный токен пользователя сессии через `WTSQueryUserToken(sessionId, out hToken)`.
     3. Дублировать токен через `DuplicateTokenEx(..., SecurityIdentification, TokenPrimary, ...)`.
     4. Сформировать блок окружения пользователя через `CreateEnvironmentBlock(out lpEnvironment, hDupToken, false)`.
     5. Запустить процесс через `CreateProcessAsUserW` с флагом `CREATE_UNICODE_ENVIRONMENT` и указанием `lpDesktop = "winsta0\\default"`.
2. **Защита от лавины процессов (Process Spawn Storm):**
   * Если UI еще загружается (холодный старт WPF занимает 0.8–1.5 сек), а служба обнаружила 10 новых коннектов от браузера, она не должна вызвать `CreateProcessAsUser` 10 раз!
   * **Решение:** Использовать в `UserSessionLauncher` глобальный именной мьютекс `Global\StartupMonitor_UI_Instance` или атомарный троттлинг запуска (`_lastUiLaunchAttemptTicks`, кулдаун не менее 15 секунд) + проверку `Process.GetProcessesByName("StartupMonitor.UI")` в целевой сессии.
3. **Что если активной сессии нет (экран блокировки `Winlogon` или RDP отключен)?**
   * Если `WTSQueryUserToken` возвращает `ERROR_NO_TOKEN` (никто не залогинен), служба не должна падать или спамить ошибками. Она должна применить политику по умолчанию (логирование + пропуск подписанных системных бинарников / блокировка Blacklist) и отложить показ алертов в очередь до момента входа пользователя (`SessionSwitch`).
