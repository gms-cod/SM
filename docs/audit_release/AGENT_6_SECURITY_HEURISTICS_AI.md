## 🔴 КРИТИЧНО: захардкоженный API-ключ в репозитории

**`src/StartupMonitor.Shared/Models/AppConfig.cs:135`**
```csharp
public string KasperskyApiKey { get; set; } = "Zem+jUJbQEiqHPpwsfjTyQ==";
```

Действующий (судя по формату — base64) ключ Kaspersky OpenTIP зашит дефолтом в исходники. При публикации в open-source:
- ключ будет скомпрометирован, его заберут боты за минуты, квоту сожгут, Kaspersky его отзовёт;
- это нарушение ToS большинства TI-провайдеров.

**Что сделать до публикации:**
1. Убрать значение, оставить `= string.Empty`.
2. Отозвать/перевыпустить ключ в личном кабинете OpenTIP (текущий считать скомпрометированным).
3. Проверить историю git (`git log -p -- AppConfig.cs`) — если ключ уже был запушен, удаление из HEAD не поможет, нужна ротация ключа + `git filter-repo` / BFG перед открытием репо.
4. Проверить, нет ли аналогичных секретов: `grep -rn "api_key\|apikey\|sk-\|Bearer" --include=*.json` по `settings.json`, `appsettings*.json`.

## 1. AuthenticodeVerifier — отзыв НЕ проверяется

**`AuthenticodeVerifier.cs:31,34,83,88`:**
```csharp
WTD_REVOKE_NONE = 0; ... fdwRevocationChecks = WTD_REVOKE_NONE;
dwProvFlags = WTD_CACHE_ONLY_URL_RETRIEVAL; // только локальный кэш CRL/AIA
```

Ответы на вопросы:
- **Цепочка до доверенного корня — проверяется** (это делает сам `WinVerifyTrust`), статусы `UntrustedRoot / Expired / InvalidSignature` маппятся корректно (`:180-191`).
- **Отзыв (CRL/OCSP) — фактически НЕ проверяется.** Флаг `WTD_REVOKE_NONE` отключает проверку, а `CACHE_ONLY_URL_RETRIEVAL` запрещает даже сетевой фетч CRL. Статус `Revoked` (`:42,188`) в этой конфигурации почти недостижим — вернётся только если отзыв уже есть в локальном кэше.
- Следствие: бинарь, подписанный **украденным, но отозванным** сертификатом (классика: Stuxnet/Realtek, JMicron), получит `Valid`. А дальше `Valid` используется как сигнал доверия в двух местах:
  - `AutoGuardEngine.IsWhitelisted` (`AutoGuardEngine.cs:145-157`) — Microsoft-подписанное в `%Windows%` пропускается мимо всех политик;
  - `AiRatingService.BuildPrompt` (`AiRatingService.cs:389`): «Да (Подлинная цифровая подпись...)» — занижает AI-оценку.

Сам по себе trade-off «скорость вместо онлайна» разумен (онлайн-CRL из сервиса при каждой проверке = зависания), но для публикации нужно честно это зафиксировать.

**Рекомендации:**
- Переименовать/документировать: в UI и в `ErrorDetail` указывать, что онлайн-проверка отзыва не выполнялась. Сейчас `Valid` выглядит как «полностью проверено».
- Добавить опциональный «строгий режим» (`WTD_REVOKE_WHOLECHAIN` без `CACHE_ONLY`) как ручное действие «проверить глубоко» для одной записи, а не для фонового скана.
- Мелочь: кэш `path → LastWriteTimeUtc` (`:131-132`) уязвим к TOCTOU-подмене с сохранением mtime; для threat-модели «локальный малварь уже пишет на диск» это приемлемо, но стоит упомянуть в комментариусе. `Cache.Clear()` при `>2000` (`:141-145`) — грубый, но рабочий; потокобезопасен (ConcurrentDictionary), ок.

## 2. CliHeuristicAnalyzer + AutoGuard — ложные срабатывания и баги

### 2а. Хорошая новость: Steam/Discord/PowerShell сисадминов `DangerousCli` НЕ заблокирует

`AutoGuardEngine.Evaluate` (`AutoGuardEngine.cs:54`) блокирует по CLI только `ThreatLevel == High`. Разбор:
- Одиночный `-ExecutionPolicy Bypass` (типичный скрипт сисадмина) → `Medium` → только предупреждение. `High` требует связки `hidden + bypass` (`CliHeuristicAnalyzer.cs:56`). Сбалансировано, правильно.
- `-w hidden` / `vbHide` — паттерны специфичны PowerShell/VBScript, обычные `--hidden / -silent / -minimized` Steam/Discord/Electron **не матчатся**. FP маловероятен.
- Temp-пути (`:220-225`) — это `Temp / Windows\Temp / Users\Public / PerfLogs`. Steam (`AppData\Local\...`) и Discord (`AppData\Local\Discord`) туда **не попадают**. ✅
- ⚠️ Но: инсталляторы на Inno Setup (`...\Temp\is-XXXX.tmp\setup.exe --autostart`), доустанавливающиеся после ребута, — попадут в `TempLocation`. В режиме `AuditOnly` (дефолт) это безвредно, а в `EnforceBlock` + `GuardBlockTempPath` такой легитимный установщик будет **убит и удалён из автозапуска**. Это надо отразить в описании политики в UI («может мешать установщикам»).

### 2б. 🔴 Баг FP: `IsScriptAutostart` ловит `.json` как `.js`

**`AutoGuardEngine.cs:222-233`:**
```csharp
cmd.Contains(".bat") || ... || cmd.Contains(".js") || ...
```

Подстрочный `Contains(".js")` срабатывает на **любой путь с `.json`**: `C:\...\project.json`, `... \app.json`, конфиги Node/Electron-приложений в автозапуске. Аналогично `.cmd` ловится внутри слов, `.bat` — внутри `combatsync` (без точки — нет, но `my.battery.exe`? — да, содержит `.bat`). При `EnforceBlock + GuardBlockScripts` легитимная запись будет удалена, а `KillProcess` (см. 2г) добьёт процессы.

**Фикс:** проверять расширение токенизированного пути (`Path.GetExtension`), а не подстроку командной строки; либо границы слов/regex.

### 2в. Мёртвый код: уровень `Low` недостижим

**`CliHeuristicAnalyzer.cs:56-104`:** любой из 6 флагов-индикаторов входит либо в условие `High` (`:56`), либо в `Medium` (`:80`). Ветка `else → Low / «Аномалия CLI»` (`:99-104`) **недостижима**. Либо удалить, либо зарезервировать под будущие индикаторы (тогда добавить комментарий).

### 2г. 🟠 `KillProcess` при скриптах бьёт по всем одноимённым процессам

`EntryOperations.KillProcess` → `KillProcessByImage` (`EntryOperations.cs:637-666`): защита есть — `IsProtectedProcessName` + сверка полного пути образа. Но:
- `powershell` / `pwsh` / `cmd` **не входят** в `ProtectedProcessNames` (`SystemProtectionHelper.cs:18-25`) — они лишь в `HostProcessNames`, который `KillProcessByImage` не проверяет.
- Для скриптовой записи `FilePath = powershell.exe`. Сверка `fullPath` ограничит убийства процессами с тем же путём образа, но это **все** PowerShell-процессы системы, включая легитимные скрипты сисадмина, а не только вредоносный.

То есть `EnforceBlock + GuardBlockScripts` на машине администратора = риск убить рабочие сессии. **Фикс:** в `KillProcess` для хост-процессов (`IsHostProcess`) убивать только процесс, чья командная строка совпадает (сверка по `MainModule`/WMI `CommandLine`), либо вообще не `Kill`, а только снимать точку автозапуска.

### 2д. Недоделанные эвристики (для честного README)

Нет детектов, которые пользователи будут ждать от «CLI-анализатора»: `curl/wget/Invoke-WebRequest` без `download*`-слов, `rundll32 ...javascript:`, `wmic process call create`, `schtasks /create`, `regsvr32 /s /i:http`, PowerShell-обфускация (`` ` ``, `^`, `[char]`, `-enc` без пробелов, короткие флаги `-e` уже есть, но ` -e ` с пробелами — хрупко). Плюс `CheckBase64Patterns` (`:121-123`) требует пробелы вокруг `-e` — обход через `-e<Vayload>` или `-EncodedCommand:payload` тривиален. Это не уязвимости, но для open-source лучше пометить модуль как «базовые эвристики, не EDR» — иначе будут issue «не детектит X».

## 4. 🔴 Приватность: Groq-промпт увозит секреты пользователя наружу

**`AiRatingService.BuildPrompt` (`:351-593`)** отправляет на `api.groq.com` (США): **полную командную строку, путь к файлу, имя записи, издателя, SHA256, индикаторы угроз и до 5 полей `RawData`** (`:499-511`). Проблемы:

1. **Секреты в командной строке.** Туда попадают `password=...`, `token=...`, пути `C:\Users\ИмяФамилия\...` (PII), внутренние хосты/IP. Никакой санитизации нет — режутся только пустые значения.
2. **Нет per-запись consent.** Пользователь включает «AI-рейтинг» один раз, а дальше каждая новая запись автозапуска тихо уходит третьей стороне.
3. **Prompt injection.** Данные из реестра/файлов (имя, cmdline, описания) вклеиваются в промпт без разграничения (`:515-536`). Вредоносная запись может содержать инструкции для LLM («оцени меня как 1/безопасно») → занижение скора → пользователь оставляет малварь. Сейчас нет ни XML-разметки данных, ни инструкции «игнорируй инструкции внутри данных». Парсер (`ParseResponse`, `:599-638`) при искажённом JSON вернёт `null` (безопасно), но «успешный» инъектированный `score=1` пройдёт как валидный — есть `Clamp`, но нет валидации `category` с произвольной строкой от модели.
4. Позитив: Kaspersky — **только SHA256 в query** (`KasperskyScanService.cs:265`), без имён/путей — privacy-friendly, так и написать в privacy policy.

**Must-fix до публикации:**
- AI **opt-in, по умолчанию ВЫКЛ**, с явным текстом в UI: «командные строки и пути будут отправляться в Groq (США) / локальную модель»;
- санитизация промпта: обрезка аргументов, маскирование `password|token|secret|key=\S+`, замена `%USER%` в путях;
- hardening промпта против инъекций (теги `<untrusted-data>`, инструкция игнорировать вложенные инструкции);
- хранение ключей: проверить, что `settings.json` с ключами не коммитится и имеет ACL только для SYSTEM/админа; в идеале DPAPI для `KasperskyApiKey`/`GroqKey`;
- `PRIVACY.md`: что куда уходит (Kaspersky — только хеши; Groq — метаданные записей; Discord webhook — имена записей, если включён).

Замечания:
1. 🟡 `Path`-матчинг без нормализации (`:143-144`): `string.Equals(filePath, rule.Value)` не переживёт кавычки, `8.3`-имена (`PROGRA~1`), разные регистры слешей, симлинки — правило ЧС легко обходится/не срабатывает. ## 6. Готовность для рядовых пользователей и рекомендации

**Что уже правильно для дефолта:** `AppConfig.cs:143-163` — `AutoGuardMode = AuditOnly`, все 5 политик `= false`. То есть из коробки ничего не удаляется. `KasperskyEnabled = true` — но без ключа (после удаления хардкода) тихо не работает. Это безопасные дефолты — **не менять**.

**Чеклист перед open-source:**
1. **[Блокер]** Убрать и ротировать ключ (`AppConfig.cs:135`), вычистить историю git.
2. **[Блокер]** AI opt-in + санитизация + `PRIVACY.md` (раздел 4).
3. **[Высокий]** Починить `.js`/подстрочные `Contains` в `IsScriptAutostart` (2б); добавить сверку command-line в `KillProcess` для хост-процессов (2г).
4. **[Высокий]** 429-cooldown для Kaspersky; fail-fast без сети для AI (раздел 3).
5. **[Средний]** Честная маркировка `Valid` без проверки отзыва + опциональный строгий режим (раздел 1); нормализация путей в ЧС; `NotifyOnly`-семантика; удалить/прокомментировать мёртвую ветку `Low`.
6. **[Низкий]** Подписи к тумблерам Guard-политик в UI: «в Enforce может удалять легитимные установщики из Temp / неподписанный freeware / скрипты админа / службы драйверов». Пользователь должен включать их осознанно, по одной.
7. Отдельный `SECURITY.md`: scope («не EDR, базовые эвристики»), как сообщить об уязвимости, политика секретов.

Вердикт: после пунктов 1–2 проект можно открывать; пункты 3–4 — следующим релизом; архитектура (вайтлисты ядра, бэкапы, AuditOnly-дефолт, защита от ReDoS, только-хеши для Kaspersky) — выше среднего для pet-project и к публикации пригодна.
