Актуальный план развития и модернизации проекта из менеджера автозагрузки в высокопроизводительную утилиту системного аудита, мониторинга процессов и безопасности (*EDR-lite / Autoruns Pro*).

> **Примечание**: Все ранее завершённые этапы (v1.0.11 – v1.9.4: Suspend/Resume, Authenticode, WMI Subscriptions, Delayed Startup, Fast Toolhelp32, UI Watchdog, Auto-Guards, OpenRouter Gemini 4 Argon) перенесены в архив истории версий и [CHANGELOG](../README.md).

## 2. Детализация активных этапов

### Этап 1: Оптимизация `ProcessMetricsTracker` и снижение периодической нагрузки CPU до 2–5% (В работе / Сегодня)

#### 1.1. 🔍 Локализация дефекта периодических всплесков CPU 12–20%
- **Симптоматика**: При открытом окне диспетчера задач или регулярном обновлении метрик процессов служба Windows демонстрирует периодические пики загрузки 12–20% CPU (что эквивалентно 100% утилизации одного или полутора логических ядер на 8-поточном процессоре).
- **Первопричина в `ProcessMetricsTracker.cs`**:
  1. Вызов стандартного .NET API `Process.GetProcesses()` каждые 1500 мс аллоцирует массив из 250–350 тяжелых объектов `Process`, каждый из которых открывает дескрипторы Win32, запрашивает имена и модули.
  2. Цикл `Parallel.ForEach(rawProcesses, new ParallelOptions { MaxDegreeOfParallelism = Math.Max(1, Environment.ProcessorCount / 2) })` каждые 1.5 секунды распараллеливает опрос 300 процессов по всем ядрам CPU.
  3. Внутри параллельного цикла на каждый процесс выполняются P/Invoke-вызовы `OpenProcess`, `GetProcessTimes`, `NtQueryInformationProcess`, опрос сокетов TCP/UDP через `ProcessNetworkTracker.GetActiveConnections()` и чтение дескрипторов ввода-вывода.
  4. Наложение параллельного обхода 300 процессов с интервалом 1500 мс кратковременно утилизирует все выделенные ядра пула потоков на 100%.

#### 1.2. 🛠 Инженерный план устранения и целевые метрики
1. **Замена `Process.GetProcesses()` на нативный `NtQuerySystemInformation`**:
   - Использование одного системного вызова ядра `ntdll.dll!NtQuerySystemInformation(SystemProcessInformation, ...)` для получения снимка всех процессов и потоков системы в едином непрерывном буфере памяти.
   - **Результат**: 0 аллокаций тяжелых объектов .NET `Process`, сокращение времени сбора снимка с 45–80 мс до 1.5–3.0 мс (ускорение в ~25–30 раз).
2. **Адаптивный интервал опроса и Time-Slicing (Пакетирование)**:
   - Увеличение базового интервала обновления метрик до 2.5–3.0 секунд в нормальном режиме.
   - Разделение сбора метрик на порции (time-slicing по 50 процессов с микропаузами 5–10 мс) вместо агрессивного `Parallel.ForEach(Cores/2)`.
3. **Разнесение фаз сбора сетевых сокетов и метрик CPU**:
   - `ProcessNetworkTracker.GetActiveConnections()` опрашивается на своей фазе с частотой не чаще одного раза в 3–5 секунд (с кэшированием таблицы TCP/UDP соединений).
4. **Интеграция с поясным балансировщиком `CpuUsageHelper`**:
   - Привязка фонового рабочего потока сбора метрик к наименее загруженному ядру через `CpuUsageHelper.AssignCurrentThreadToIdealCore()`.
   - Принудительное понижение приоритета рабочего потока до `ThreadPriority.Lowest` / `SetThreadPriority(THREAD_PRIORITY_LOWEST)`.
5. **Целевой результат**:
   - Снижение периодических пиков нагрузки процессора со службы с 12–20% до стабильных **2–5% максимум** при открытом мониторе и **0.0–0.5%** при свернутом UI.

### Этап 2: Событийное ядро ETW (Event Tracing for Windows — Zero-Polling EDR)

- **Проблема**: Любой опрос (таймерный поллинг процессов через 1–3 секунды) создает вычислительные накладные расходы и теоретически может пропустить короткоживущие вредоносные процессы (droppers/stagers), которые отрабатывают за 200–500 мс и завершаются.
- **Решение**: Подписка на системный провайдер ядра Windows `Microsoft-Windows-Kernel-Process` через библиотеку `Microsoft.Diagnostics.Tracing.TraceEvent`.
- **Эффект**:
  - Нулевая нагрузка на CPU в моменты отсутствия активности в ОС (0.00% CPU).
  - Мгновенное получение событий `ProcessStart` и `ProcessStop` с PID, точной командной строкой и токеном пользователя за < 1 мс.
  - Мгновенное применение правил `AutoGuardEngine` до того, как вредоносный процесс успеет закрепиться или нанести ущерб.

### Этап 3: Поведенческий AI-анализ аномалий сетевого трафика (Traffic Behavioral Scorer)

- **Назначение**: Выявление скрытых C2-каналов управления ботнетами и троянами.
- **Возможности**:
  - Мониторинг периодичности исходящих запросов к удаленным IP (Beaconing Detection — регулярные пинги раз в N секунд с джиттером);
  - Детектирование нестандартных протоколов на системных портах (например, не-HTTP трафик на порту 80/443);
  - Эвристика соотношения входящего/исходящего трафика (аномальный объем отправленных данных при отсутствии входящего).
