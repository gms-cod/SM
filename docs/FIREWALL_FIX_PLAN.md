# Комплексный план модернизации Firewall & Окон уведомлений (v1.9.3-plan)

## 1. Итоги исследований роя OpenCode и причины проблем

В ходе глубокого аудита кодовой базы StartupMonitor с участием 3 специализированных субагентов (`opencode/nemotron-3.5-super-vl-free`, `opencode/mimo-v2.6-flash-free`, `opencode/deepseek-v4.1-flash-free`) были детально локализованы все выявленные корневые проблемы:

### Проблема №1: Фаервол работает и выдает уведомления только при открытой вкладке UI
- **Корневая причина 1 (Фоновый сервис)**: В `src/StartupMonitor.Service/Services/Firewall/NetworkConnectionAlertService.cs` (строка 177) цикл сканера управляется предикатом:
  ```csharp
  hasWork: () => AlertsEnabled && _monitorWindowActive
  ```
  Когда пользователь переключается на другую вкладку или сворачивает приложение в трей, вызывается `SetMonitorWindowActive(false)`. Фоновый поток сканирования соединений переходит в состояние бесконечного ожидания `Timeout.InfiniteTimeSpan` и не производит опрос сетевых соединений.
- **Корневая причина 2 (UI Poller)**: В `src/StartupMonitor.UI/Views/NetworkSecurityHubView.xaml.cs` (строки 252-272, 289-305) таймер опроса очереди алертов `_alertPollerTimer` объявлен и привязан исключительно к жизненному циклу `NetworkSecurityHubView`. При уходе со страницы срабатывает `Deactivate()`, останавливая таймер. В `MainViewModel` глобальный поллер отсутствует.

### Проблема №2: Зацикливание окна алертов (баг Opera) и некорректная работа списков
- **Корневая причина 1 (Нормализация пути и имени)**: В `NetworkConnectionAlertService.ResolveAlert` (строки 348-356) при разрешении `WhitelistProgram` в `_whitelistedApps` сохранялся только точный путь приложения (`appKey = path`). Однако для многопроцессных браузеров (Opera, Chrome, Edge) дочерние процессы (GPU, сетевые воркеры, рендереры) часто возвращают через `ResolveProcessPath` относительные подпапки версий (например, `...\Opera\105.0.4970.21\opera.exe`), либо сетевой сокет кратковременно сообщает только имя процесса `opera.exe` при `path == null`. В результате проверка `IsWhitelistedApp(null, "opera.exe")` возвращала `false`.
- **Корневая причина 2 (Очередь событий)**: При нажатии «Добавить в белый/черный список» уже накопившиеся в очереди `_pendingById` и `_queue` алерты для этого же приложения не очищались мгновенно, вызывая повторные всплывающие окна сразу после закрытия текущего.
- **Корневая причина 3 (Черный список)**: В модели `NetworkAlertResolution` отсутствовали явные перечисления для персистентного черного списка (`BlacklistProgram`) и запрета на сеанс (`BlockSession`). Приложение не сохраняло заблокированные программы в настройках и не создавало безусловные правила блокировки.

### Проблема №3: Оптимизация производительности (0% CPU в простое)
- При работе в фоне вызов `_firewallService.GetAllRules()` производит дорогостоящую COM-итерацию по всем правилам Windows Firewall каждые 5 секунд при каждом тике сканера.
- **Решение**: Кеширование путей правил фаервола (`_firewallRulePathsCache`) с временем жизни (TTL 60 с) и событийно-ориентированной инвалидацией при создании/изменении правил через приложение.

## 2. Архитектурный план доработки (To-Do для реализации)

### Блок A. Модель данных и конфигурация
1. **`NetworkAlertResolution` (`NetworkAlertModels.cs`)**:
   - `WhitelistProgram = 1` — разрешить навсегда, сохранить в конфиге, подавить любые алерты.
   - `BlacklistProgram = 5` — запретить навсегда: создать системное блокирующее правило Windows Firewall, сохранить в конфиге, подавить любые алерты.
   - `AllowSession = 2` — разрешить на текущий сеанс работы программы (без постоянного правила).
   - `BlockSession = 6` — запретить на текущий сеанс работы программы (без постоянного правила).
   - `CreateRule = 7` — открыть диалог детального создания правила для приложения.
2. **`AppSettings` (`AppConfig.cs`)**:
   - Добавить свойство `public List<string> FirewallBlacklistedApps { get; set; } = new();`
   - Обеспечить корректное клонирование списка в методе `Clone()`.

### Блок B. Логика ядра (`NetworkConnectionAlertService.cs`)
1. **Автономность сканирования**:
   - Изменить условие активности на: `hasWork: () => AlertsEnabled` (независимо от активности UI-вкладки).
2. **Двухуровневый надежный матчинг (Path + ProcessName)**:
   - При добавлении в `_whitelistedApps` и `_blacklistedApps` сохранять как полный нормализованный путь, так и имя исполняемого файла (`Path.GetFileName(path).ToLowerInvariant()`).
   - Метод `IsWhitelistedApp` и `IsBlacklistedApp` обязан проверять совпадение по обоим ключам.
3. **Реакция на действия пользователя**:
   - При `WhitelistProgram`: мгновенная очистка всех ожидающих алертов для данного приложения в `_pendingById` и `_queue`.
   - При `BlacklistProgram`: мгновенная очистка очереди, блокировка соединения, создание правила блокировки через `IFirewallService.AddRuleAsync(...)` и сохранение в постоянный конфиг.
   - При `BlockSession`: временное занесение в сессионный черный список `_sessionBlockedApps`.
4. **Оптимизация 0% CPU**:
   - Внедрить `_firewallRulePathsCache` (кешированный `HashSet<string>`) для быстрой проверки `IsKnownFirewallApp` с инвалидацией только при изменении правил или раз в 60 секунд.

### Блок C. Глобальный опрос алертов в UI (`StartupMonitor.UI`)
1. **Перенос поллера в `MainViewModel.cs`**:
   - Разместить `_networkAlertPollerTimer` в `MainViewModel`.
   - Таймер работает непрерывно (интервал 1.5–2 сек), когда включены алерты, обеспечивая всплывание окна при нахождении на любой вкладке и при работе из системного трея.
2. **Очистка `NetworkSecurityHubView.xaml.cs`**:
   - Удалить дублирующий `_alertPollerTimer` из представления `NetworkSecurityHubView`.

### Блок D. Обновление окна `NetworkConnectionAlertWindow` (5 кнопок)
1. **XAML (`NetworkConnectionAlertWindow.xaml`)**:
   - Переработать блок кнопок действий в удобную раскладку с 5 кнопками:
     1. `[+] Добавить программу в белый список` (Зеленый акцент / Success) — полностью разрешено, 0 алертов.
     2. `[-] Добавить программу в чёрный список` (Красный акцент / Danger) — полностью запрещено, 0 алертов.
     3. `[~] Разрешить на сеанс` (Нейтральный) — временное разрешение.
     4. `[x] Запретить на сеанс` (Оранжевый) — временный запрет.
     5. `[*] Создать правило для приложения` (Информационный) — запуск мастера правил.
2. **Code-behind (`NetworkConnectionAlertWindow.xaml.cs`)**:

   - Возврат соответствующего enum `NetworkAlertResolution` в вызывающий сервис.
